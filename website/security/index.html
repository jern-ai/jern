Security and data flow

The boundary is explicit.

Jern Cloud begins as a control plane. Customer-managed GitHub Actions runners execute the open-source runtime and retain all model credentials. Cloud authenticates runs, reserves admission capacity, and stores encrypted evidence.

The concise claim: repository policy is enforced in the open-source runtime; process tools rely on OS confinement and policy; Cloud authorization is bound to GitHub identity; retained trace bytes are encrypted before database persistence.

What stays in your environment

  • Source checkout and working tree
  • GitHub Actions runner and its process environment
  • Anthropic, OpenAI, or other provider credentials
  • Direct model-provider requests and billing relationship
  • The active Jern runtime and policy enforcement

What reaches Jern Cloud

  • GitHub installation, repository, actor, workflow, ref, commit, and run identity
  • A requested per-run token reservation and lifecycle status
  • The completed Jern JSONL trace and receipt evidence
  • User identity and selected-repository access during dashboard authorization

Traces may contain prompts, tool inputs, outputs, and file content observed by the agent. The API encrypts the exact uploaded bytes with AES-256-GCM before PostgreSQL persistence. The run ID is authenticated as additional data so ciphertext cannot be reassigned to another run.

Credentials

Provider keys are ordinary customer GitHub environment secrets. They are not Action inputs or Cloud request fields. Browser OAuth access tokens, GitHub App JWTs, installation tokens, and Actions OIDC tokens are short-lived and remain in memory. Cloud persists only digests of browser session and run-upload credentials.

Repository setup authority

Inspection uses a short-lived App token restricted to one selected repository and contents read. Creating a setup pull request additionally requires the signed-in GitHub user to have write authority. The write token is restricted to that repository and to contents, workflows, and pull requests. Cloud creates a branch and reviewable pull request; it does not merge, dispatch workflows, or manage secrets.

Honest limits

  • A compromised customer runner can bypass Jern and use credentials available to that runner.
  • Cloud reservation is admission control, not independently authenticated provider metering.
  • Approved shell commands execute as processes; language-level capabilities do not confine them.
  • Cloud does not currently claim compliance certification, customer-managed encryption keys, or data residency.
  • Jern governs Jern runtime sessions, not arbitrary sessions from other coding-agent products.

Verify the implementation

The runtime security model, GitHub Action, policy implementation, receipt derivation, and trace vocabulary are public under Apache-2.0. Security-sensitive reports can use GitHub private vulnerability reporting.
